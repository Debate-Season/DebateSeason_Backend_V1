## 0. 한눈에

**무엇**: 이슈 하나당 **나무위키식 문서 1장**. 배경·쟁점·찬반 논거를 서술한 백과사전형 문서를 **AI가 생성**하고,
ADMIN 검수 후 게시한다. 유저 협업 편집은 미래(리비전 구조만 지금 잡아둔다).

**왜 백엔드인가**: 문서는 **미리 생성해 DB에 저장**하고 API는 싸게 서빙만 한다(요청마다 LLM 호출 ❌ — 지연·비용·중립성).
저장·서빙·검수·버전관리는 전형적 백엔드 도메인. 생성(LLM 호출)도 이번엔 백엔드가 맡는다(원천 재료가 앱 DB의
이슈·스레드에 있으므로).

**규모(2026-07-25 prod 실측)**: 이슈 17, 스레드(옛 방) 26, CONTAINER 17. → 위키 대상은 이슈 17장.

**핵심 결정 (이 문서에서 확정)**
| 항목 | 결정 | 근거 |
|---|---|---|
| 앵커 | **이슈당 1장** (issue 1:1 wiki) | "나무위키식" = 주제당 문서 1장. 스레드는 문서 안의 쟁점 절로 참조 |
| 본문 저장 | 메타(`debate_wiki`) + 본문 이력(`debate_wiki_revision`) 분리 | 위키의 본질은 **개정 이력**. AI 재생성·롤백·미래 인간편집이 모두 리비전 추가로 안전 |
| 게시 | **DRAFT → PUBLISHED (ADMIN 승인)** | 정치·시사 문서라 자동 게시 금지. 중립성·사실 검수 게이트 필수 |
| 생성기 | Anthropic **Claude (Opus 4.8)**, 백엔드에서 호출 | 원천(이슈·스레드)이 앱 DB에 있음. Java SDK로 배치성 호출 |
| 실시간성 | 사전 생성·캐시 | 요청 시 생성 금지 |

## 1. 현재 상태 (prod 실측)

- **위키 테이블 없음**(`SHOW TABLES` 확인). v1.3.4 PRD 의 `DebateWiki` 설계는 **미구현**.
- `IssueEntity`: `title`, `major_category`, `middle_category`, `status`, timestamps. **요약/본문 필드 없음.**
- 데이터 파이프라인(`toronchul_data_v1`)의 `create_issue`/`keyword`/`media_keyword` 는 앱 `issue` 와 **별개**.
  이번 위키는 앱 `issue` 를 앵커로 하고, 파이프라인 데이터는 (선택) 생성 재료로만 참조.
- 배치 인프라 존재: `domain/youtubeLive/scheduler/*` 의 `@Scheduled` 패턴 재사용 가능.
- LLM/HTTP 연동: YouTube API용 WebClient/RestTemplate 패턴은 있으나 **AI 클라이언트는 없음**(신규).

## 2. 데이터 모델

```
DebateWiki (debate_wiki)                        ── 이슈당 1장 (메타)
 ├ wiki_id            PK
 ├ issue_id           FK, UNIQUE   ← 이슈 1:1
 ├ status             DRAFT / PUBLISHED / HIDDEN
 ├ published_revision_id   현재 게시 중인 리비전 (NULL=미게시)
 └ created_at, updated_at

DebateWikiRevision (debate_wiki_revision)       ── 본문 이력 (append-only)
 ├ revision_id        PK
 ├ wiki_id            FK
 ├ content            본문 (Markdown)
 ├ source             AI / ADMIN        ← 생성 주체
 ├ model              생성 모델명 (예: claude-opus-4-8), ADMIN 편집은 NULL
 ├ edit_summary       변경 요약 (예: "최초 AI 생성", "사실 오류 수정")
 ├ created_by         ADMIN 편집 시 user_id, AI 생성은 NULL
 └ created_at
```

**설계 근거**
- 위키=개정 이력이 본질. 본문 컬럼을 `debate_wiki` 에 붙이지 않고 **리비전으로 분리** →
  AI 재생성=새 리비전, ADMIN 편집=새 리비전, 롤백=`published_revision_id` 를 옛 리비전으로 되돌림.
- `issue_id UNIQUE` → 이슈당 1장 강제. 이슈에 방/스레드가 없어도 위키는 가질 수 있다.
- 게시 상태의 단일 진실은 `debate_wiki.status` + `published_revision_id`. 서빙은 이 조합만 본다.
- DDL: `docs/sql/v1.4.0-wiki.sql` (Expand — 신규 테이블 2개, 기존 무영향).

## 3. API

### 3.1 서빙 (신 클라이언트) — Phase 1
`GET /api/v2/wiki?issue-id={id}` (optional-auth)
- 그 이슈의 **게시된(PUBLISHED)** 위키 본문 1건. 미게시/미존재는 `data:null` + 200(에러 아님).
- 응답:
  ```json
  { "issueId": 6, "issueTitle": "...", "status": "PUBLISHED",
    "content": "## 개요\n...", "model": "claude-opus-4-8",
    "revisionId": 12, "updatedAt": "..." }
  ```
- `WebSecurityConfig.OPTIONAL_AUTH_URLS` 에 `/api/v2/wiki` 추가. 렌더링(Markdown→HTML)은 클라이언트.

### 3.2 생성·검수 (ADMIN) — Phase 2
- `POST /api/v1/admin/wiki/generate?issue-id={id}` — LLM 으로 초안 생성 → **DRAFT 리비전** 저장(게시 안 함).
  응답에 생성된 `revisionId` + 본문 미리보기.
- `POST /api/v1/admin/wiki/publish` (body: `{revisionId}`) — 해당 리비전을 게시(`status=PUBLISHED`,
  `published_revision_id=revisionId`).
- `POST /api/v1/admin/wiki/revisions` (body: `{issueId, content, editSummary}`) — ADMIN 수동 편집 리비전 추가.
- 경로는 `/api/v1/admin/**` → `WebSecurityConfig` 에서 이미 `hasRole("ADMIN")`. 추가 설정 불필요.

### 3.3 이력 (선택) — Phase 3
`GET /api/v2/wiki/revisions?issue-id={id}` — 리비전 목록(diff/롤백 UI용).

## 4. AI 생성 (Phase 2 설계)

**호출 위치**: 백엔드 `WikiGenerationService`. ADMIN 트리거(우선) + (선택) `@Scheduled` 배치.
**SDK**: `com.anthropic:anthropic-java`. 클라이언트 `AnthropicOkHttpClient.fromEnv()` (`ANTHROPIC_API_KEY`).
**모델**: `claude-opus-4-8` (기본). 긴 본문이라 **streaming + `max_tokens` 넉넉히(≤128K)** + `.get_final_message()`.
adaptive thinking(`ThinkingConfigAdaptive`), effort=`high`.

**생성 컨텍스트(원천 재료, 앱 DB에서 조립)**
- 이슈 `title` + `major/middle_category`
- 그 이슈의 스레드(옛 방) 제목들 = 주요 쟁점 목록
- (선택) 스레드별 대표 채팅 일부, 파이프라인 `keyword`
- (선택) **웹 검색 그라운딩**: `web_search_20260209` 서버툴로 최신 사실 확인 → 환각 완화(시사 문서라 중요). 비용↑, Phase 3 옵션.

**가드레일 (정치·시사 필수)**
- 시스템 프롬프트에 **중립·균형·출처 표기** 강제. 한쪽으로 기울지 않게 찬/반 논거를 대칭 서술.
- **자동 게시 금지** — 항상 DRAFT 로 저장, ADMIN 검수 후 PUBLISHED.
- 재생성은 "원천이 바뀌었을 때만"(스레드 추가/활동 임계치) → 비용 통제. 매 조회 생성 ❌.

**출력 형식**: Markdown 본문(개요 / 배경 / 타임라인 / 쟁점별 찬반 / 참고). 구조는 프롬프트로 고정.

## 5. Phase 계획

| Phase | 내용 | 외부 의존 |
|---|---|---|
| **1 (구현 중)** | 스키마(DDL) + 엔티티/리포 + 서빙 API(`GET /api/v2/wiki`, published 조회) + security 허용 + 테스트 | 없음 (provider-agnostic) |

| **3** | 리비전 이력 API + (선택) 웹검색 그라운딩 + `@Scheduled` 재생성 + 홈/이슈상세 위키 노출 | 프론트 협업 |

## 6. 열린 결정 (Phase 2 착수 전 필요)

1. **`ANTHROPIC_API_KEY`** — 발급/보관. 서버 `/home/ubuntu/app/.env` 에 추가(비밀, 출력 금지). 없으면 Phase 2 불가.
2. **생성 트리거** — ADMIN 수동만 vs `@Scheduled` 야간 배치 병행. (권장: 우선 수동, 안정화 후 배치)
3. **웹검색 그라운딩** — 지금부터 넣을지(사실성↑·비용↑) vs 모델 지식만으로 시작. (권장: 시작은 모델 지식, Phase 3 에서 web_search)
